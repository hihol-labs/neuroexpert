# DECISIONS — журнал проектных решений (append-only)

> **Контракт непрерывности.** Один файл на проект, решения дописываются В КОНЕЦ
> и не переписываются задним числом (отмена решения = новая запись со ссылкой
> на старую). Это канонический ответ на вопрос «почему здесь так» для следующей
> сессии/агента с амнезией — session-файлы памяти дают хронологию, DECISIONS.md
> даёт выжимку, которая переживает архивацию памяти.
>
> **Что сюда писать:** решения, которые влияют на будущие правки — выбор
> технологии/подхода, отвергнутые альтернативы, договорённости с заказчиком,
> сознательные trade-off'ы. **Что НЕ писать:** ход работ (это session-файлы),
> большие пивоты архитектуры (это ADR через `/strategy` — сюда только
> однострочную ссылку на ADR).
>
> Кто пишет: `/session-save` (Step 3.2) дописывает решения сессии автоматически;
> любой скилл может дописать решение в момент принятия. Формат записи — ниже.

## Формат записи

```markdown
## YYYY-MM-DD: <решение одной строкой>
- Почему: <причина — факты, не мнение>
- Отвергнуто: <альтернатива> (<почему нет>)
- Ограничение: <что это решение накладывает на будущий код, если накладывает>
- Ссылки: <unit U-N / PR #N / ADR-NNN / session_YYYY-MM-DD.md>
```

Поля «Отвергнуто»/«Ограничение»/«Ссылки» — опциональны, «Почему» — обязательно.

## 2026-08-16: Публикация 56 коммитов через git push --no-verify — осознанный обход publication-гейта
Почему: гейт требовал полный keyless-producer route (~час работы); риск отсутствия офсайт-копии 56 коммитов оценён пользователем как выше, чем риск непроверенного провенанса. Решение принято пользователем явно, после того как обе опции были предъявлены.
Отвергнуто: прогнать keyless route целиком (час); отложить push (риск потери работы на одной машине сохранялся бы).
Ограничение: keyless-producer evidence по этим коммитам НЕ существует — провенанс опубликованного кода гейтом не подтверждён. Отметка о происхождении артефакта не должна ссылаться на этот push как на пройденный гейт.
Ссылки: push 0b8ff79..5cef388 в codex/plan-north-star-marketing-contract, .itd-memory/session_2026-08-16.md блокер №2.

## 2026-08-16: Основной путь доставки на прод — gate-артефакт (DEPLOY_MODE=artifact), git-режим legacy
Почему: на проде /opt/neuroexpert — rsync-дерево без .git, поэтому checkout по SHA и git ls-files на сервере неприменимы. Артефакт (архив коммита + sha256, сверяемый на сервере до распаковки) — тот же объект, который принимает pre-release-гейт.
Отвергнуто: восстанавливать git-клон на проде (сервер обслуживает чужой Coolify-стек, лишний git-remote и ключи — новая поверхность); держать rsync рабочего дерева как основной путь (тянет untracked-мусор в build context).
Ограничение: инвариант «деплоится только опубликованное» теперь проверяется ЛОКАЛЬНО (origin-tip), на сервере проверять нечем; осознанный обход — ALLOW_UNPUSHED=1. Дерево приводится к артефакту через rsync --delete: серверный кэш .turbo (667 МБ) будет удалён при первом запуске, сохраняются только .env, рендеренный kong.yml, lock и .deploy-backups. Живой прогон нового пути на проде НЕ выполнялся.
Ссылки: коммит b6c7753, scripts/deploy.sh шаги 1 и 4.

## 2026-08-16: Кандидат деплоя сверяется с квитанцией по git-tree, а не по SHA коммита
Почему: квитанция гейта фиксирует candidate.reviewedTree (отревьюированное ДЕРЕВО), а не идентификатор коммита — на момент ревью кандидат мог быть ещё незакоммиченным. Проверено на реальном инциденте: reviewedTree fdcfe209 совпадает с tree задеплоенного c6b5717, а у документационного коммита 2f1d52c, который в прошлый раз незаметно подменил кандидата, tree другой (27b073d) — сверка по дереву ловит ровно этот класс подмены.
Отвергнуто: сверять по SHA коммита из квитанции (такого поля нет); доверять HEAD (это и был дефект).
Ограничение: scripts/check-gate-receipt.mjs проверяет ПРИВЯЗКУ кандидата к квитанции, но не подпись квитанции и не качество ревью; осознанный обход — ALLOW_UNGATED=1.
Ссылки: scripts/check-gate-receipt.mjs, scripts/deploy.sh шаг 0.

## 2026-08-16: Граница ревью G-010b — транспортная правка deploy.sh заморожена на достигнутом
Почему: 21 раунд независимого ревью дал 52 находки, все закрыты, но последние восемь раундов
находки шли почти целиком по scripts/deploy.sh, а не по предмету юнита (оффер и оракул). Каждая
правка транспорта открывает следующий слой гонок; предмет юнита стабилен с раунда 17. Решение
принято пользователем после предъявления трёх вариантов: сузить ревью до юнита, гнать до
PASSED на общем дифе, вынести deploy.sh в отдельный юнит.
Отвергнуто: гнать до нуля находок на общем дифе (часы работы без гарантии сходимости — каждая
правка рождает новую поверхность); отдельный юнит под deploy.sh (два круга ревью вместо одного,
ровно то, чего пункт 0b должен был избежать).
Ограничение: остаток по deploy.sh — гипотетические гонки при ОДНОВРЕМЕННЫХ деплоях (порог
протухания lock против ретраев, чередование шагов двух релизов, накопление .part при серии
обрывов). У соло-оператора одновременных деплоев не бывает; на многооператорном сценарии эти
пути НЕ проверены и заявлять их безопасными нельзя. Закрытые в раундах 1-21 дефекты покрыты
регрессиями в scripts/tests/ (6 наборов, run-all.sh).
Ссылки: .itd-memory/verification-loop/prompts/G-010b-round{1..21}-prompt.md, scripts/tests/run-all.sh.

## 2026-08-22: План v4 (AEO-слой) утверждён; ADR-002 и цены не меняются

Утверждён `AEO_PLAN.md` — единый план реализации с учётом 8 AEO/GEO-методик из папки
пользователя, market-scan 2026-08-19 и разборов business-analyst/devils-advocate.
В леджер добавлены G-015 (AEO сайта: FAQ+FAQPage JSON-LD, /llm-info, TL;DR),
G-016 (Яндекс.Вебмастер + Bing Webmaster + IndexNow, AI-сегмент Метрики),
G-017 (отчёт аудита v2 + письменная методика внедрения); критерии G-012 и G-013 дополнены.

Почему: все изученные источники подтверждают нишу ADR-002, а не опровергают её —
«AI-видимость» как заголовок продукта уже красный океан (бесплатные проверки Faros,
GEO Scout на 12 провайдерах), незанятое окно — локальный бизнес + аудит 4 точек входа
+ внедрение. Новое из методик — это КАК делать аудит и сайт, а не ЧТО продавать.

Отвергнуто:
- Поднять цену аудита до 20-40k ₽ (рыночный коридор). Коридор взят из прайсов-хотелок
  агентств с sales-командой и портфолио; у соло-фаундера без кейсов нет носителя такой
  цены, а цикл сделки удлиняется на 2-4 недели при 37 днях до чекпоинта. Решение по цене —
  на чекпоинте 2026-09-28 по ≥10 названным вслух ценам в SALES_LOG.
- Подключить «Алису» к сканеру. У ассистента Алиса нет публичного API; прогон YandexGPT
  под названием «Алиса» = overclaim того же класса, что зачищали 2026-04-19/20. Ключ
  YandexGPT — в icebox (AEO-ICE-1), в UI называть «YandexGPT».
- Создавать llms.txt. Эффект не подтверждён на выборке 129k доменов (SE Ranking);
  вместо него страница /llm-info со ссылкой из футера.
- Переписывать заголовки лендингов под «продвижение в нейросетях» — возврат в красный
  океан; термин допустим только в тексте блока про ИИ (его ищут маркетологи, не владельцы клиник).

Ограничение: запрещены принципиально — скрытые промпты в HTML, клоакинг под AI-ботов,
keyword stuffing, гарантии позиций в ответах LLM, непроверяемые цифры в маркетинге.
Приоритет остаётся за фазой C (продажи руками): AEO-слой не открывается, пока не
закрыты G-010b…G-014.

Ссылки: AEO_PLAN.md, MARKET_BRIEF.md (блоки 2026-08-19 и 2026-08-22),
CURRENT_PLAN.md (фаза B+), BACKLOG.md (AEO-ICE-1…5), .itd-memory/session_2026-08-22.md.

## 2026-08-30: Курс на self-serve — «Аудит 7 900» становится автономным продуктом

Какое: модель доставки меняется с «форма заявки → человек» на самообслуживание.
Первым автономным делается ровно один пакет — «Аудит Старт» 7 900 ₽: регистрация →
онлайн-оплата → автоматический прогон работ → артефакт в кабинете + письмо, без
участия человека. Остальные пакеты пока не трогаем.

Почему: владелец указал, что текущий сайт читается как форма сбора заявок, а не как
продукт («зашёл, зарегался, оплатил и получил автоматически»), и это удорожает поиск
клиентов. Проверка кода подтвердила диагноз: разрыв ровно один — факт оплаты не
порождает работу. Регистрация (Supabase magic link), webhook ЮKassa payment.succeeded
и worker с 19 job-типами уже есть, но не соединены.

Отвергнуто:
- Автоматизировать все пакеты сразу — «Запуск Старт» 31 100 ₽ физически не
  автоматизируется без доступов к ресурсам клиента (Яндекс.Бизнес, 2ГИС, сайт);
  обещание «оплатил → получил всё» на нём даёт возвраты, а не продажи.
- Свернуть G-011 ради скорости — ручной путь «счёт → акт» остаётся запасным для
  B2B-клиентов, которым нужны закрывающие документы.

Ограничение (граница честности не меняется): автоматизируется анализ и план.
Внедрение по-прежнему делает клиент, платформа проверяет факт. «Запуск Старт»
остаётся услугой и должен быть явно помечен как требующий доступов и участия
человека — иначе декларация разойдётся с кодом.

Конфликт с ADR-002, снят владельцем: auth и полная интеграция ЮKassa стояли в фазе D
(«после 5 оплат»). Решением владельца они вытаскиваются вперёд — self-serve признан
способом получить те самые первые оплаты, а не наградой за них.

Ссылки: GOAL.json (G-011 verified 2026-08-30), apps/web/app/api/webhooks/yukassa/route.ts,
apps/worker/src/jobs/, apps/web/app/(marketing)/launch/page.tsx, CURRENT_PLAN.md фаза B.

обработкой исключений, продажами и необязательной консультацией, но не производят
штатную delivery. Первый автономный продукт — Audit Start 7 900 руб.

Почему: путь «заявка → сотрудник» не масштабируется без роста штата и читается рынком
как агентство. Проверка кода показала, что автономный контур почти построен (регистрация,
webhook кассы, worker с 19 job-типами) и не соединён в одном месте — факт оплаты не
порождает работу.

Три правки внесены владельцем ДО перевода в ACCEPTED:

1. G-011b переведён в `deferred`, а не закрыт — решение от 2026-08-27 о выводе
   мультиплатформенности из icebox сохраняет силу. Условие выхода: `YANDEX_FOLDER_ID`
   в прод-env И оплаченный ключ DeepSeek; при выполнении возвращается в очередь
   без нового решения владельца.
2. Acceptance блока AF-1 разделён: «3-5 внешних оплат» вынесены в отдельный
   коммерческий gate `AF-1-COMM`. Рыночный результат не входит в инженерный acceptance,
   не блокирует закрытие AF-1 и не занимает WIP, но остаётся условием открытия AF-2.
   Причина: иначе при WIP=1 блок нельзя закрыть до реакции рынка, и очередь встаёт
   бессрочно.
3. В AF-0 добавлено приведение маркетинговых страниц в соответствие с границей
   автоматизации по каждому платному SKU. Причина: граница честности из ADR §3/§5
   должна доехать до публичного текста, иначе Managed Lite подаётся как подписка
   на автоматику, которой ещё нет.

Отвергнуто: немедленный `/strategy` с переписыванием тарифов и всей воронки — тот же
режим «разработка вместо продаж», из которого вытащил ADR-002 (0/5 оплат, 0/300 подписчиков).

Ограничение: ADR-002 сохраняет силу в части acquisition (фаза C как ежедневный
последовательный cadence — sales-квота ДО кода), цен и чекпоинтов 2026-09-28 / 2026-10-15.
Цены заморожены до gate AF-1-COMM. Публичный шаг покупки остаётся dark до готовности
обеих стадий G-018 и G-019 и включается атомарно.

## 2026-08-30: Ниши платного аудита расширяются локальными вертикалями

Какое: список ниш платного аудита расширяется локальными вертикалями (стоматология

Почему: продавать выбрано стоматологиям, а движок платного аудита эту вертикаль
не покрывает — заказ вернул бы 500 на этапе загрузки вопросов.

1. Миграция в public.niches: id, name, slug, icon, is_focus, seed_keywords
   (packages/supabase/migrations/004_seed_niches.sql — образец).
2. NICHE_NAMES в apps/web/app/api/audit/route.ts:349 — список продублирован
   хардкодом в коде поверх канонической таблицы niches. Техдолг: при расширении

3. Наполнение таблицы questions (source=wordstat, is_active): без строк для новой

archive или bounded replay), новые ниши могут не наполниться. Ниши и очередь
не независимы — порядок работ это учитывает.

- Продавать экспертам из существующего списка — расходится с выбором стоматологий

## 2026-08-30 — Очередь `expand_query`: archive, не bounded replay (юнит AF-0)

Какое: 754 исторических упавших задачи `expand_query` архивируются; ни массового,
ни частичного replay. Провайдерный путь проверяется канарейкой на одном НОВОМ
`expand_query` — этот пункт уже есть в acceptance AF-0.

Почему (диагностика `.itd-memory/diagnostics/expand-query-queue-2026-08-30.md`):
1. `expand_query` не завершался успешно ни разу: живой `/api/health` от
   2026-08-30T19:09:28Z — `completed=0, failed=754, pending=0, processing=0`,
   `scheduled_retries` пуст. Причина системная (оба LLM-провайдера были
   недоступны на этом пути), а не построчная.
2. Множество не менялось с прод-снимка 2026-06-14 (754 тогда и сейчас; прирост
   completed ровно +12 — шесть новых типов задач по две). Уникальность по
   `payload.question_id` из того снимка остаётся в силе: в неизменном множестве
   дубли появиться не могли.
3. Артефакт задачи — `sub_queries` — не читает ни один SKU автономного контура.
   Потребители: блок «похожие вопросы» на публичных страницах, примеры в
   TG-уведомлении и Knowledge API `/api/v1/blind-spots`. Последний — платный
   (Pro-план), но он вне автономного контура AF-1, и платящих агентств у него
   сейчас ноль (тикет `B-003`). Ценность replay для AF-1 нулевая; для Knowledge
   API она появится только вместе с первым платящим агентством.
4. Очередь ломает единственный доступный сигнал наблюдаемости: `failed_jobs` в
   `/api/health` постоянно 754, и новое падение на 3-5 задач в этом фоне не
   видно. Автономная delivery без честного сигнала не проверяема.

Уточнение прежней записи от 2026-08-30 (решение по нишам): формулировка «вопросы
наполняет worker (collect-demand, expand-query)» и вывод «пока решение по 754 не
принято, новые ниши могут не наполниться» — неточны. `questions` наполняет только
`collect_demand` (`collect-demand.ts:152`); `expand_query` пишет в `sub_queries`
(`expand-query.ts:85`). Заказ по ненаполненной нише падает с 503
(`api/audit/route.ts:524`), а не с 500. Связь очереди с G-018 сохраняется, но она
операционная: `find_gaps` создаёт до 50 задач на прогон, поэтому до зелёной
канарейки сбор спроса по новым вертикалям не включается.

Как исполняется (тикет `QUEUE-1`, отдельный юнит: нужен доступ по SSH и
data-sensitive гейт): строки не удаляются; до мутации снимается построчный
снимок; изменение статуса ограничено `type='expand_query' AND status='failed' AND
created_at < '2026-08-31'` с ожидаемым числом 754 (иначе откат); значение
`archived` добавляется в CHECK миграцией; health считает archived отдельно от
failed.

Когда пересматривается: если при фиксации report schema (пункт AF-0) `sub_queries`
войдут в состав платного отчёта — тогда bounded replay 20 задач ПОСЛЕ зелёной
канарейки. Иначе решение окончательное.

Ограничение доказательства: построчные запросы к прод-БД сейчас недоступны — SSH
на 185.221.213.104 не проходит (timeout during banner exchange, перехват
WARP/VPN). Уникальность и разбор текстов ошибок опираются на прод-SQL снимок
2026-06-14 плюс машинное доказательство неизменности множества.

## 2026-09-08 — R-01: дизайн сверки платежей (в рамках утверждённого плана ADR-004)

Какое: (1) сверка «от нас»: worker раз в 15 мин делает GET /v3/payments/{id} по pending/expired-

## 2026-09-09 — R-05: хранилище и cron экспертов (в рамках утверждённого плана ADR-004)

Какое: (1) миграция 031 создаёт расширение `pg_cron` и расписания `weekly-demand` /
`weekly-generate-orders` идемпотентно (`cron.unschedule` одноимённых + `cron.schedule` с телами
003/008); guard в начале миграции падает, если GUC `cron.database_name` не совпадает с целевой БД;
(2) bucket `voice` переведён в приватный с лимитами (25 МиБ, `allowed_mime_types audio/*`), чтение —
через новый роут `/api/audio/<voice_id>`: проверка «есть опубликованная статья», `createSignedUrl`
в момент запроса, 302, `no-store` на всех ветках; (3) бот и `/api/voice` обязаны загрузить аудио в
Storage ДО записи `voice_recordings`, при ошибке — ответ пользователю и 500, без записи и без STT;
(4) health отдаёт `cron {extension, jobs}` и `storage {voice_bucket}` через RPC `infra_status()`
(SECURITY DEFINER, EXECUTE только service_role — PostgREST не видит схемы `cron` и `storage`);
(5) остальные расписания 003 (citations/serp/trust/sitemap/freshness) сознательно вне scope — их
job-типы принадлежат R-08/R-11.

Почему: диагноз прода 2026-09-08 показал, что `pg_cron` никогда не создавался — миграции 003/008
числились применёнными, а `cron.job` не существовал, то есть еженедельный сбор спроса не запускался
ни разу; активация пары при оплате (R-03) без cron ничего не давала. Bucket `voice` был создан
вручную и публичен: аудио экспертов открывалось по прямой ссылке. Подписанная ссылка, «запечённая»
в ISR-страницу, протухала бы в кэше редкой статьи — отсюда стабильный роут с подписью в момент
запроса. Отвергнуто: включить все расписания 003 сразу (их job-типы не готовы), оставить bucket
публичным (регрессия безопасности), подписывать ссылку в самой странице (протухание в кэше).
Ограничение: `supautils` в образе `supabase/postgres` выполняет after-create скрипт расширения от
имени роли `supabase_admin`, которой на self-hosted БД нет — миграция заводит роль-плейсхолдер
`SUPERUSER NOLOGIN` (без пароля, вход невозможен); без неё не установится ни одно privileged-
расширение из списка supautils. `ALTER ROLE ... NOLOGIN` сознательно не делается: на настоящем
Supabase это рабочая login-роль платформы.

## 2026-09-09 — Активные пары в cron: выключатель вместо инварианта (временно)

Какое: живые прогоны оракулов идут с `SELFSERVE_PAIRS_ACTIVATED=1`; проверка «`local_pairs.active`
= 0» из §5 G-018b больше не отражает реальность.
Почему: правило писалось, когда пары включались в cron только вручную решением владельца. С R-03
пара активируется автоматически при оплате, с R-05 cron по ней реально собирает спрос — активная
пара «Стоматология · Тюмень» есть следствие оплаченного заказа, то есть цель, а не аномалия.
Отвергнуто: деактивировать пару на проде (это рабочая целевая пара, и следующий оплативший клиент
всё равно активирует свою); менять инвариант внутри R-05 (юнит уже прошёл шесть коммитов и
двенадцать раундов чекеров — раздувать scope хуже, чем записать долг).
Ограничение: пока стоит выключатель, «самопроизвольная» активация пары без оплаты не будет поймана
оракулом. Настоящий инвариант — health отдаёт «активные пары без оплаченного заказа» — записан
тикетом PAIR-2 в BACKLOG.

## 2026-09-09 — R-05' (R-05b): отчёт показывает деньги, а не только проблемы

Какое: в план вставлен юнит R-05' сразу после R-05. Форма заказа получает два необязательных поля
(средний чек и конверсия из обращения в сделку); отчёт получает денежный блок — упущенная выручка
открытой формулой «частотность Wordstat × доля вопросов, где клиента не называют × конверсия ×
чек» с подписью источника каждого множителя (Wordstat / наш замер / ваши цифры); без введённых
клиентом цифр блок не показывается.
Почему: решение владельца — «отчёт должен показывать деньги, а не проблемы, иначе не покупают».
Сейчас отчёт говорит на техническом языке (gap-score 7/10, «не хватает источников»), а посчитать
деньги нечем: форма собирает только сайт, конкурентов и «что уже пробовали».
Отвергнуто: считать деньги по отраслевым средним (нарушает «только измеренные данные, никаких
выдуманных цифр», SELF_SERVE_PLAN п.148); спрашивать цифры обязательными полями (барьер перед
оплатой). Ограничение: два множителя из четырёх — допущение клиента и названы как его допущение;
доля «клиента не называют» берётся из нашего замера и честно ограничена десятью вопросами.
